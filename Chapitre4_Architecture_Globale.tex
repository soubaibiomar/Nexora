\section{Introduction}
% ══════════════════════════════════════════════════════════════

Ce chapitre présente l'architecture globale du projet Nexora en détaillant les choix technologiques, l'organisation des composants, les mécanismes de collecte des données et les pipelines de traitement. L'architecture a été conçue pour répondre aux exigences de performance, de scalabilité et de maintenabilité identifiées dans le cahier des charges, tout en intégrant des processus de collecte et de transformation des données adaptés au contexte Big Data du projet.

\section{Architecture 3-Tiers}
% ══════════════════════════════════════════════════════════════

L'application Nexora suit une architecture \textbf{3-tiers} séparant strictement la présentation, la logique métier et les données :

\begin{verbatim}
  +---------------------------------------------------+
  |            Couche Presentation (Frontend)          |
  |   React 18 + TypeScript + Material UI + Vite       |
  |   react-force-graph-3d (WebGL/Three.js)            |
  +----------------------+----------------------------+
                         | HTTP REST / WebSocket
  +----------------------v----------------------------+
  |              Couche Metier (Backend)                |
  |   FastAPI + Uvicorn (API REST)                     |
  |   +--------------+  +--------------------+        |
  |   |  Moteur ML   |  |  Auth + RBAC (JWT) |        |
  |   |  PageRank    |  +--------------------+        |
  |   |  TF-IDF      |  +--------------------+        |
  |   |  Collab.Filt.|  |  Kafka Simulator   |        |
  |   |  Classifier  |  |  Spark Batch       |        |
  |   +--------------+  +--------------------+        |
  +----------------------+----------------------------+
                         | Bolt (Cypher) / File I/O
  +----------------------v----------------------------+
  |              Couche Donnees                        |
  |   Neo4j 5 (Graph DB)  +  Fichiers JSONL            |
  +---------------------------------------------------+
\end{verbatim}

\section{Collecte des Données}
% ══════════════════════════════════════════════════════════════

\subsection{Stratégie de Collecte}

Dans le cadre de Nexora, la collecte des données suit une approche en \textbf{deux temps} adaptée au contexte du projet :

\begin{enumerate}
    \item \textbf{Phase 1 — Génération synthétique :} Un générateur de données (\texttt{generate\_data.py}) produit des jeux de données réalistes simulant une grande organisation. Cette approche permet de tester l'ensemble du pipeline sans dépendre de données réelles.
    
    \item \textbf{Phase 2 — Intégration de sources réelles (extensible) :} L'architecture est conçue pour accueillir des connecteurs vers des sources de données d'entreprise (SIRH, LDAP, GitHub, Jira, Slack).
\end{enumerate}

\subsection{Sources de Données}

\begin{longtable}{|p{3cm}|p{3.5cm}|p{2.5cm}|p{4.5cm}|}
\hline
\rowcolor{bleu!15}
\textbf{Source} & \textbf{Type de données} & \textbf{Format} & \textbf{Fréquence} \\
\hline
Générateur Python & Employés, Skills, Projets, Documents & JSONL & À la demande (ponctuel) \\
\hline
SIRH (futur) & Profils, départements, organigramme & API REST & Quotidien \\
\hline
GitHub (futur) & Contributions, langages, repos & API REST & Temps réel (webhooks) \\
\hline
Jira (futur) & Tickets, assignations, compétences déduites & API REST & Horaire \\
\hline
LMS / e-learning & Certifications, formations complétées & API / CSV & Hebdomadaire \\
\hline
\end{longtable}

\subsection{Processus de Collecte Actuel}

Le processus de collecte actuel repose sur le script \texttt{generate\_data.py} qui suit les étapes suivantes :

\begin{enumerate}
    \item \textbf{Initialisation :} Configuration du seed aléatoire et des paramètres d'échelle.
    \item \textbf{Génération des compétences :} Création du référentiel de 82 compétences réparties en 6 catégories.
    \item \textbf{Génération des employés :} Création des profils avec attribution réaliste des compétences basée sur l'affinité département-compétence.
    \item \textbf{Génération des documents :} Création des publications avec attribution aux auteurs (employés existants).
    \item \textbf{Génération des projets :} Création des projets avec constitution des équipes (échantillonnage parmi les employés).
    \item \textbf{Sérialisation :} Écriture des données au format JSONL dans le dossier \texttt{data/}.
\end{enumerate}

\section{Pipeline d'Ingestion dans Neo4j}
% ══════════════════════════════════════════════════════════════

Une fois les données collectées (fichiers JSONL), elles sont ingérées dans la base de données Neo4j selon le processus suivant :

\subsection{Chargement des Nœuds}

\begin{lstlisting}[language={}]
// 1. Creation des noeuds Expert
LOAD CSV FROM 'file:///employees.jsonl' AS line
CREATE (e:Expert {
  id: line.id,
  name: line.name,
  email: line.email,
  department: line.department,
  role: line.role,
  location: line.location,
  experience_years: line.experience_years
})

// 2. Creation des noeuds Skill
LOAD CSV FROM 'file:///skills.jsonl' AS line
CREATE (s:Skill {
  id: line.id,
  name: line.name,
  category: line.category,
  demand: line.demand
})
\end{lstlisting}

\subsection{Création des Relations}

\begin{lstlisting}[language={}]
// Relations HAS_SKILL (Expert -> Skill)
MATCH (e:Expert), (s:Skill)
WHERE s.name IN e.skills
CREATE (e)-[:HAS_SKILL {level: skill.level}]->(s)

// Relations WORKS_ON (Expert -> Project)
MATCH (e:Expert), (p:Project)
WHERE e.id IN p.team_members
CREATE (e)-[:WORKS_ON]->(p)

// Relations AUTHORED (Expert -> Document)
MATCH (e:Expert), (d:Document)
WHERE e.id = d.author
CREATE (e)-[:AUTHORED]->(d)
\end{lstlisting}

\subsection{Indexation}

\begin{lstlisting}[language={}]
// Index pour performances de requetage
CREATE INDEX expert_id FOR (e:Expert) ON (e.id)
CREATE INDEX skill_name FOR (s:Skill) ON (s.name)
CREATE INDEX project_id FOR (p:Project) ON (p.id)
CREATE INDEX document_id FOR (d:Document) ON (d.id)
\end{lstlisting}

\section{Architecture de Déploiement}
% ══════════════════════════════════════════════════════════════

\subsection{Conteneurisation Docker}

L'application est entièrement conteneurisée via \textbf{Docker Compose}, orchestrant trois services :

\begin{verbatim}
  docker-compose.yml
  |
  +-- neo4j (Image: neo4j:5-community)
  |   +-- Ports : 7474 (Browser UI), 7687 (Bolt)
  |   +-- Volume : neo4j_data (persistant)
  |   +-- Env : NEO4J_AUTH=neo4j/nexorapass
  |   +-- Plugins : APOC
  |   +-- Healthcheck : neo4j status (15s interval)
  |
  +-- backend (Build: backend/Dockerfile)
  |   +-- Port : 8000
  |   +-- Base : Python 3.11-slim
  |   +-- Volume : ./data -> /app/data
  |   +-- Env : NEO4J_URI, NEO4J_USER, NEO4J_PASSWORD
  |   +-- Depends : neo4j (condition: service_healthy)
  |
  +-- frontend (Build: frontend/Dockerfile)
      +-- Port : 3000 -> 80
      +-- Build multi-stage :
      |   +-- Stage 1 : Node 20 (npm build -> dist/)
      |   +-- Stage 2 : Nginx Alpine (serve dist/)
      +-- Nginx conf : SPA routing + API proxy
      +-- Depends : backend
\end{verbatim}

\subsection{Configuration Nginx}

Nginx joue un double rôle dans l'architecture :

\begin{enumerate}
    \item \textbf{Serveur de fichiers statiques :} Sert les fichiers compilés React (HTML, JS, CSS) et gère le fallback SPA (toutes les routes non-fichier redirigées vers \texttt{index.html}).
    \item \textbf{Proxy inverse :} Redirige les requêtes \texttt{/api/*} vers le backend FastAPI (port 8000), incluant le support WebSocket pour le chat temps réel.
\end{enumerate}

\subsection{Ordre de Démarrage et Dépendances}

\begin{verbatim}
  1. Neo4j demarre (healthcheck: 15s interval, max 5 retries)
     |
     v
  2. Neo4j healthy -> Backend demarre
     |  (charge les JSONL, initialise les modeles ML)
     |
     v
  3. Backend pret -> Frontend demarre
     |  (Nginx ecoute sur le port 3000)
     |
     v
  4. Application operationnelle
\end{verbatim}

\section{Sécurité et Authentification}
% ══════════════════════════════════════════════════════════════

\subsection{Flux d'Authentification JWT}

\begin{verbatim}
  +-------------------------------------------------+
  |              FLUX AUTHENTIFICATION                |
  +-------------------------------------------------+
  |                                                 |
  |  1. Client envoie POST /api/auth/login          |
  |     Body: { username, password }                |
  |                                                 |
  |  2. Backend verifie :                           |
  |     +-- Rate limiting (5 tentatives / 5 min)    |
  |     +-- bcrypt.verify(password, hashed_pwd)     |
  |                                                 |
  |  3. Si valide -> Generation JWT :               |
  |     { sub: "username", role: "admin",           |
  |       exp: now + 24h }                          |
  |     Signe avec cle secrete (HS256)              |
  |                                                 |
  |  4. Client stocke le token (localStorage)       |
  |                                                 |
  |  5. Requetes suivantes :                        |
  |     Header: Authorization: Bearer <token>       |
  |     -> Backend decode, verifie role,            |
  |       autorise ou refuse (403)                  |
  |                                                 |

\section{Conclusion}
% ══════════════════════════════════════════════════════════════

L'architecture de Nexora a été conçue pour offrir un équilibre optimal entre \textbf{performance}, \textbf{modularité} et \textbf{extensibilité}. Les choix technologiques — Neo4j pour la modélisation en graphe, FastAPI pour l'API performante, React pour l'interface réactive, Docker pour le déploiement reproductible — forment un ensemble cohérent et moderne.

Le processus de collecte des données, s'appuyant sur un générateur synthétique configurable, garantit la disponibilité de jeux de données réalistes et reproductibles pour alimenter l'ensemble des composants : graphe de connaissances, moteur ML et analyses Big Data.

Cette architecture est conçue pour évoluer : l'ajout de nouveaux connecteurs de données (SIRH, GitHub, Jira), de nouveaux algorithmes ML, ou le passage à un cluster Neo4j/Spark en production ne nécessite qu'une extension modulaire des composants existants, sans refonte structurelle. Cette approche « API-First » et conteneurisée assure la pérennité et la maintenabilité du système.
