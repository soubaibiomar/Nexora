\section{Introduction}
% ══════════════════════════════════════════════════════════════

Ce document présente la conception détaillée de la plateforme \textbf{Nexora}. Il décrit l'architecture logicielle, les diagrammes UML (cas d'utilisation, classes, séquences), le modèle de données en graphe, ainsi que les algorithmes d'IA/ML utilisés. L'objectif est de fournir une vue technique claire du fonctionnement interne du système.

\section{Architecture Générale}
% ══════════════════════════════════════════════════════════════

\subsection{Architecture 3-Tiers}

L'application Nexora suit une architecture \textbf{3-tiers} classique, séparant la présentation, la logique métier et les données :

\begin{verbatim}
  ┌───────────────────────────────────────────────────┐
  │            Couche Présentation (Frontend)          │
  │   React 18 + TypeScript + Material UI + Vite       │
  │   react-force-graph-3d (WebGL/Three.js)            │
  └──────────────────────┬────────────────────────────┘
                         │ HTTP REST / WebSocket
  ┌──────────────────────▼────────────────────────────┐
  │              Couche Métier (Backend)                │
  │   FastAPI + Uvicorn (API REST)                     │
  │   ┌──────────────┐  ┌────────────────────┐        │
  │   │  Moteur ML   │  │  Auth + RBAC (JWT) │        │
  │   │  PageRank    │  └────────────────────┘        │
  │   │  TF-IDF      │  ┌────────────────────┐        │
  │   │  Collab.Filt.│  │  Kafka Simulator   │        │
  │   │  Classifier  │  │  Spark Batch       │        │
  │   └──────────────┘  └────────────────────┘        │
  └──────────────────────┬────────────────────────────┘
                         │ Bolt (Cypher) / File I/O
  ┌──────────────────────▼────────────────────────────┐
  │              Couche Données                        │
  │   Neo4j 5 (Graph DB)  +  Fichiers JSONL            │
  └───────────────────────────────────────────────────┘
\end{verbatim}

\subsection{Explication des Couches}

\begin{itemize}[leftmargin=*]
    \item \textbf{Couche Présentation :} Application SPA (Single Page Application) React servie par Nginx. Communique avec le backend via des requêtes REST (axios). Le graphe 3D utilise WebGL via Three.js pour le rendu temps réel.
    \item \textbf{Couche Métier :} API REST FastAPI qui contient toute la logique métier : authentification, RBAC, moteur de recommandation ML, pipelines Big Data. Le serveur ASGI Uvicorn gère les connexions HTTP et WebSocket (chat).
    \item \textbf{Couche Données :} Neo4j stocke les entités (Expert, Skill, Project, Document) et leurs relations dans un graphe. Les fichiers JSONL servent de source de données pour les modèles ML et les analyses Spark.
\end{itemize}

\section{Diagrammes de Séquence}
% ══════════════════════════════════════════════════════════════

\subsection{Séquence : Authentification (Login)}

\begin{verbatim}
  Client         Nginx         FastAPI        bcrypt         JWT
    │               │              │              │             │
    │ POST /login   │              │              │             │
    │ (user, pass)  │              │              │             │
    │──────────────>│              │              │             │
    │               │──forwards──>│              │             │
    │               │              │──verify()──>│             │
    │               │              │<──true──────│             │
    │               │              │──encode()───────────────>│
    │               │              │<──token──────────────────│
    │               │<──{token}───│              │             │
    │<──{token}─────│              │              │             │
    │               │              │              │             │
    │ GET /experts  │              │              │             │
    │ (Bearer token)│              │              │             │
    │──────────────>│              │              │             │
    │               │──forwards──>│              │             │
    │               │              │──decode()───────────────>│
    │               │              │<──{sub,role}─────────────│
    │               │              │──check role──│             │
    │               │<──data──────│              │             │
    │<──data────────│              │              │             │
\end{verbatim}

\textbf{Explication :}
\begin{enumerate}[leftmargin=*]
    \item Le client envoie les identifiants via POST.
    \item Nginx redirige la requête vers FastAPI (proxy inverse).
    \item FastAPI vérifie le mot de passe avec bcrypt (hachage + comparaison).
    \item Si valide, FastAPI génère un JWT contenant le username et le rôle.
    \item Pour les requêtes suivantes, le client envoie le token dans le header \texttt{Authorization}.
    \item FastAPI décode le token et vérifie le rôle avant de répondre.
\end{enumerate}

\subsection{Séquence : Recommandation d'Expert}

\begin{verbatim}
  Client         FastAPI       Recommender     Embeddings     JSONL
    │               │              │              │             │
    │ POST /ai/     │              │              │             │
    │ recommend     │              │              │             │
    │ (query)       │              │              │             │
    │──────────────>│              │              │             │
    │               │──recommend()>│              │             │
    │               │              │──if not trained──────────>│
    │               │              │<──load profiles───────────│
    │               │              │──fit_tfidf()─>│             │
    │               │              │<──vectors─────│             │
    │               │              │──transform()─>│             │
    │               │              │<──query_vec───│             │
    │               │              │──cosine_sim()─│             │
    │               │              │──sort top K───│             │
    │               │<──results────│              │             │
    │<──[experts]───│              │              │             │
\end{verbatim}

\textbf{Explication :}
\begin{enumerate}[leftmargin=*]
    \item Le client envoie une requête textuelle décrivant le besoin.
    \item Le Recommender charge les profils experts depuis les fichiers JSONL (si pas déjà en mémoire).
    \item Les profils sont vectorisés via TF-IDF (Term Frequency--Inverse Document Frequency).
    \item La requête est transformée dans le même espace vectoriel.
    \item La similarité cosinus est calculée entre la requête et chaque profil.
    \item Les K experts les plus similaires sont retournés avec leurs scores.
\end{enumerate}

\subsection{Séquence : PageRank des Experts}

\begin{verbatim}
  Client         FastAPI       PageRank        JSONL Files
    │               │              │              │
    │ GET /ai/      │              │              │
    │ expert-rank   │              │              │
    │──────────────>│              │              │
    │               │──rank()─────>│              │
    │               │              │──load()─────>│
    │               │              │<──data───────│
    │               │              │──build graph──│
    │               │              │  (Expert<->Skill<->Project)
    │               │              │──iterate x20──│
    │               │              │  (d=0.85)     │
    │               │              │──blend scores─│
    │               │              │  (60% graph   │
    │               │              │   40% features)│
    │               │<──rankings───│              │
    │<──[ranked     │              │              │
    │   experts]    │              │              │
\end{verbatim}

\textbf{Explication :}
\begin{enumerate}[leftmargin=*]
    \item Un graphe biparti est construit à partir des données (Expert $\leftrightarrow$ Skill $\leftrightarrow$ Project).
    \item L'algorithme PageRank itère 20 fois avec un facteur d'amortissement $d = 0.85$.
    \item Le score final combine le rang PageRank (60\%) avec des caractéristiques individuelles (40\%) : diversité des compétences, nombre de projets, documents publiés, et années d'expérience.
\end{enumerate}

\begin{verbatim}
                    ┌──────────┐
                    │  Topic   │
                    └────▲─────┘
                         │ COVERS_TOPIC
                    ┌────┴─────┐
                    │ Document │
                    └────▲─────┘
                         │ AUTHORED

  │ Skill │◄────────────│  Expert  │────────────>│ Project │
  └───┬───┘              └────┬────┘              └────┬────┘
      │                       │                        │
      │    REQUIRES_SKILL     │      KNOWS             │
      └◄──────────────────────┼────────────────────────┘
                              │
                         ┌────▼────┐
                         │ Expert  │
                         └─────────┘
\end{verbatim}

\subsection{Propriétés des Nœuds}

\begin{longtable}{|p{2.5cm}|p{11cm}|}
\hline
\textbf{Nœud} & \textbf{Propriétés} \\
\hline
Expert & id, name, email, department, role, location, experience\_years, expertise\_level, hire\_date, skills[] \\
\hline
Skill & id, name, category, level, demand \\
\hline
Project & id, name, domain, status, priority, budget, tech\_stack[], required\_skills[], team\_members[] \\
\hline
Document & id, title, type, topic, content, author, date, views, rating \\
\hline
Topic & id, name \\
\hline
\end{longtable}

\subsection{Pourquoi Neo4j ?}

\begin{itemize}[leftmargin=*]
    \item \textbf{Parcours de graphe efficaces :} trouver les experts liés à une compétence en temps constant (pas de jointures SQL coûteuses).
    \item \textbf{Langage Cypher :} requêtes déclaratives naturelles pour les patterns de graphe (\texttt{MATCH (e:Expert)-[:HAS\_SKILL]->(s:Skill)}).
    \item \textbf{PageRank natif :} la structure de graphe est directement exploitable par les algorithmes de centralité.
    \item \textbf{Flexibilité du schéma :} pas de schéma rigide, facile d'ajouter de nouvelles relations.
\end{itemize}

\section{Conception du Déploiement}
% ══════════════════════════════════════════════════════════════

\begin{verbatim}
  docker-compose.yml
  │
  ├── neo4j (port 7474, 7687)
  │   └── Volume : neo4j_data (persistant)
  │   └── Healthcheck : cypher-shell
  │
  ├── backend (port 8000)
  │   ├── FastAPI + Uvicorn
  │   ├── Monte : ./data -> /app/data
  │   └── Dépend de : neo4j (healthy)
  │
  └── frontend (port 3000 -> 80)
      ├── Build : Node 20 (build) -> Nginx Alpine (serve)
      ├── Routing SPA : fallback index.html
      ├── Proxy : /api/* -> backend:8000
      └── Dépend de : backend
\end{verbatim}

\textbf{Explication :}
\begin{itemize}[leftmargin=*]
    \item \textbf{Neo4j} démarre en premier avec un healthcheck pour s'assurer qu'il est prêt avant le backend.
    \item \textbf{Le backend} ne démarre que quand Neo4j est \textit{healthy}. Il monte le dossier \texttt{data/} pour accéder aux fichiers JSONL.
    \item \textbf{Le frontend} est compilé en production (Vite build), puis servi par Nginx qui gère aussi le proxy API vers le backend.
\end{itemize}
